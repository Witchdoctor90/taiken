# CLAUDE.md — Taiken Core

Цей файл агент читає на початку кожної сесії. Він навмисно короткий: що робити, чого не робити
і де шукати решту. Структура репо й правила залежностей живуть у README папок і підключені нижче —
тут вони не дублюються.

## Що це

Бекенд сервісу оплати й лояльності для закладів Албанії. Гість сканує QR столика в Telegram Mini App,
бачить рахунок із POS, платить на сторінці PSP і отримує штамп на картці лояльності.

Модульний моноліт на .NET 10, Postgres, Wolverine + EF Core outbox. Стадія — MVP (M0–M7):
POS і PSP — фейки за портами, Telegram — справжній канал.

## Команди

```sh
dotnet restore
dotnet build --no-restore                         # warnings = errors
dotnet format --verify-no-changes --no-restore    # стиль з .editorconfig
dotnet test --no-build
dotnet run --project src/Host/Taiken.Api          # /health/live, /health/ready
```

Ті самі кроки виконує CI (`.github/workflows/dotnet.yml`).

## Готово — це коли

Зміна завершена, лише якщо:

- `dotnet build` — 0 warnings, 0 errors;
- `dotnet format --verify-no-changes` чистий;
- `dotnet test` зелений, і нова поведінка покрита тестом;
- не порушене жодне правило з цього файлу чи README;
- нова конвенція, якщо зміна її вводить, дописана сюди або в README відповідної папки.

Не вимикай warnings (`#pragma warning disable`, `NoWarn`) і не послаблюй `Directory.Build.props`
чи `.editorconfig`, щоб пройшов білд. Виправ причину або спитай.

## Структура і правила залежностей

@README.md
@src/Modules/README.md
@src/Integrations/README.md
@src/BuildingBlocks/README.md
@src/Fakes/README.md
@tests/README.md

Коротко:

- `src/Host/Taiken.Api` — єдиний composition root. Тільки він посилається на реалізації модулів і адаптерів.
- Модуль = `Taiken.<Name>.Contracts` + `Taiken.<Name>`. Інші модулі бачать лише `Contracts`.
- Порт і canonical-моделі — `Integrations/<Kind>/Taiken.<Kind>.Abstractions`, адаптери поруч.
- Фейк — окремий процес. На нього не посилається ніхто, і він не посилається ні на що з `src/`.
  Адаптер говорить із фейком **лише по HTTP**, через власні `internal` DTO — так само, як говоритиме
  зі справжньою системою.

## Принцип: нічого наперед

Каркас мінімальний навмисно: він росте за конвенцією, а не за заготовками.

- Проєкт створюється разом із першим кодом у ньому. Порожніх проєктів «на майбутнє» не буває.
- Абстракція (інтерфейс, базовий клас, generic-хелпер) з'являється, коли є ≥2 реальні споживачі.
  Один споживач — конкретний клас. Виняток — порти в `*.Abstractions`: це межа із зовнішньою системою.
- У `BuildingBlocks` потрапляє лише те, що вже повторилось у ≥2 модулях.
- Жодних «про всяк випадок» параметрів, конфігурації, feature flags, точок розширення.

Якщо здається, що без заготовки не обійтись, — спитай.

## Конвенції коду

- **Мова.** Код, ідентифікатори, лог-повідомлення — англійською. README, ADR — українською.
- **Видимість.** У реалізації модуля й адаптера все `internal`. Виняток — Wolverine handlers: `public`,
  бо Wolverine за замовчуванням знаходить лише public-типи. Межу модуля тримають ArchitectureTests,
  а не модифікатори доступу.
- **Реєстрація модуля.** `AddXModule(this IServiceCollection, IConfiguration)` +
  `MapXEndpoints(this IEndpointRouteBuilder)`. Host лише викликає їх.
- **Провайдери.** Адаптер реєструється як keyed service з ключем, що збігається зі значенням
  `pos_provider` / `psp_provider` закладу. Модуль отримує адаптер за ключем, не знаючи конкретного типу.
- **Пакети.** Версії — тільки в `Directory.Packages.props` (CPM), у `.csproj` — `PackageReference`
  без `Version`. Новий пакет — згадати в описі PR з поясненням навіщо.
- **Ідентифікатори** — strongly-typed з SharedKernel (`VenueId`, `CustomerId`, …), не голі `Guid`.
- **Помилки домену** — `Result<T>`, не винятки. Виняток — для справді виняткового (впала інфраструктура).
- **Час** — лише через `TimeProvider` з DI. `DateTime.Now` / `DateTime.UtcNow` заборонені.
- **Маппінг** зовнішнього формату в canonical — явний код в адаптері. Без AutoMapper і рефлексії.

## Інваріанти, які не можна порушити

Кожен захищає гроші гостя або дані закладу. Якщо задачу не виконати, не порушивши один із них, —
це не задача, а питання: зупинись.

**Гроші й платежі**

- Taiken ніколи не бачить і не зберігає дані картки (PAN, CVV, термін дії). Оплата — лише на
  сторінці провайдера (PCI DSS SAQ A).
- Гроші — `Money`: мінорні одиниці в `long` + валюта ISO 4217. Не `double` / `float`.
- Суми з POS авторитетні: `Total` береться з джерела, не перераховується з рядків чека.
- Оплату зараховує лише server-to-server webhook із перевіреним підписом або reconciler через
  `GetStatusAsync`. `postMessage` з браузера і редірект — тільки UX, ніколи не джерело правди.
- `ProviderPaymentStatus.Unknown` ніколи не стає успіхом. Успіх — лише коли `captured == amount`.
- Зміна стану і публікація події (`PaymentCompleted` тощо) — в одній транзакції через outbox.
- Кожен обробник webhook або повідомлення ідемпотентний: повторна доставка не змінює результат
  (унікальний індекс на джерелі + inbox).

**Дані й ізоляція**

- Venue-scoped дані фільтруються по `VenueId` через EF Global Query Filter. `IgnoreQueryFilters()` —
  лише в явно дозволених місцях (reconciler, вхідний webhook) і з коментарем, чому.
- `Customers` — глобальний модуль, поза фільтром по `VenueId`. Телефон у форматі E.164 — canonical
  identity клієнта; Telegram та інші канали — лише способи входу до того самого акаунта.
- Кожен модуль — своя схема Postgres і свої міграції. **Жодних FK між схемами модулів**:
  id з іншого модуля — просто значення.
- Модуль не читає таблиці іншого модуля. Тільки через його `Contracts`.

**Безпека**

- Секрети — не в репо: user-secrets локально, `.env` на сервері. Облікові дані PSP закладу
  зберігаються зашифрованими (ASP.NET Data Protection).
- Не логувати: секрети, токени, підписи, повний Telegram `initData`, сирі тіла webhook із
  персональними даними. Телефон у логах — маскований.

## Тести

- Інтеграційні тести — проти справжнього Postgres через Testcontainers. EF InMemory і SQLite замість
  Postgres заборонені: вони не перевіряють query filters, транзакції, унікальні індекси й `xmin`.
- Кожен новий запит до venue-scoped даних — тест ізоляції: заклад A не бачить даних закладу B.
- Кожен адаптер проходить contract tests свого `Kind` у `Taiken.ContractTests` (fixtures + snapshot).
- Назва тесту описує поведінку: `Unknown_never_maps_to_success`, а не `Test1` чи `MapTest`.

## Робочий процес

- Одна задача = один issue `TAI-N` = одна гілка (назва з Linear: `mrvnalexandr/tai-n-...`).
- Коміти: `TAI-N: <що змінено>`, англійською, в наказовому способі.
- Роби рівно скоуп issue. Знайдену проблему поза скоупом опиши у фінальному звіті, не виправляй мовчки.
- **Новий модуль:** папка + 2 проєкти за `src/Modules/README.md`, запис у `Taiken.slnx`, реєстрація
  в Host, власна схема БД. Якщо в модуля є власні інваріанти — `CLAUDE.md` у папці модуля.
- **Новий провайдер (POS / PSP / канал):** 1 проєкт у `Integrations/<Kind>/`, contract tests,
  keyed-реєстрація в Host. Модулі не змінюються — якщо довелось змінити модуль, порт спроєктовано погано: спитай.
- **Нове архітектурне рішення** — ADR за `docs/adr/0000-template.md`.

## Коли зупинитись і спитати

- джерела (issue, ADR, README, дизайн) суперечать одне одному;
- щоб виконати задачу, треба порушити правило залежностей або інваріант;
- потрібна залежність між модулями, якої немає в `Contracts`;
- потрібен новий NuGet-пакет або зовнішній сервіс;
- міграція видаляє чи перейменовує колонки або таблиці з даними;
- зміна впливає на те, коли і скільки грошей списується чи зараховується.

## Як цей файл росте

Тут — лише те, що стосується всього репо. Правила конкретного модуля (стан-машина `PaymentIntent`,
ledger лояльності) живуть у `CLAUDE.md` всередині папки модуля: Claude Code підтягує такий файл,
коли працює з файлами цієї папки. Приклади коду — посиланнями на реальні файли в репо, не вставками.
