# 0005. Автентифікація: персонал і клієнти — окремі схеми

## Статус

Proposed

## Контекст

У системи дві принципово різні групи користувачів.

**Гості (клієнти).** Заходять через Telegram Mini App, пароля не мають. Акаунт глобальний: одна
людина — картки в кількох закладах (ADR 0009). Особу підтверджує канал: Telegram підписує `initData`,
телефон приходить як контакт у бот. Після MVP з'являться інші канали (web, нативний застосунок).

**Персонал.** Власники закладів, адміністратори, офіціанти, а також команда Taiken. Входять логіном і
паролем в адмінку. Належать до одного або кількох закладів із певною роллю. Саме з їхніх даних
береться контекст закладу (ADR 0002). У MVP адмінки майже немає, але модель має бути закладена
правильно.

Вимоги:

- токен гостя за жодних обставин не відкриває endpoint персоналу, і навпаки;
- автентифікація гостя не прив'язана до Telegram як до єдиного каналу;
- мінімум власного security-коду і жодного окремого identity-сервера на одному домашньому сервері.

## Рішення

### Дві незалежні схеми автентифікації

- У хості зареєстровані дві схеми: `Customer` і `Staff`. Кожна група endpoints вимагає рівно
  одну з них через політику авторизації. Endpoint, який приймає обидві, заборонений.
- Токени мають різні `audience`. Навіть підписаний правильним ключем токен гостя не проходить
  валідацію схеми `Staff`.
- Webhooks провайдерів не використовують жодної з цих схем: вони анонімні на рівні автентифікації
  й перевіряються підписом провайдера (ADR 0012).

### Гості — модуль Customers, власний JWT

- Вхід через верифікатор каналу (`IExternalIdentityVerifier`): для Telegram — HMAC-перевірка
  `initData` і свіжість `auth_date`. Верифікатор повертає підтверджену зовнішню особу; Customers
  знаходить або створює за нею акаунт (телефон — canonical identity, ADR 0009).
- Taiken видає власний короткоживучий access token (порядку години): `sub` = `CustomerId`,
  `aud` = `customer`. `VenueId` у токені немає: гість глобальний, заклад визначається ресурсом
  (ADR 0002).
- Refresh-токенів у MVP немає. TMA при кожному запуску і після закінчення токена повторно
  автентифікується через `initData`.
- Токен передається як `Authorization: Bearer` і тримається в пам'яті TMA, не в `localStorage`.
- Валідація — стандартний `JwtBearer`; видача — `JsonWebTokenHandler`. Ключ підпису — із секретів,
  з `kid`, щоб ротація не потребувала зміни коду.

### Персонал — ASP.NET Core Identity

- Акаунти персоналу — ASP.NET Core Identity у власній схемі БД окремого модуля (з'являється разом
  із першим endpoint персоналу, не раніше).
- Членство — пари (`VenueId`, роль). Ролі MVP: власник закладу, персонал закладу; окремо —
  адміністратор платформи.
- Адмінка працює з того самого домену, тому автентифікація персоналу — cookie Identity
  (`HttpOnly`, `Secure`, `SameSite=Strict`) з antiforgery, без токенів у JavaScript.
- Заклад для запиту персоналу береться з маршруту (`/venues/{venueId}/…`) і перевіряється проти
  членства користувача. Лише після цього встановлюється контекст закладу. Токен або cookie самі по
  собі заклад не визначають.

### Спільне

- Ключі ASP.NET Data Protection (cookie персоналу, шифрування облікових даних PSP) персистуються
  поза контейнером і входять у бекап. Втрата ключів = розлогінений персонал і нечитабельні
  credentials закладів.
- У документах OpenAPI (ADR 0003) кожен документ описує лише свою схему: `customer` — bearer.
- Адмінки фейків (Fake POS, Fake PSP) захищені Cloudflare Access, а не автентифікацією Taiken.

### Відхилені альтернативи

- **Одна ASP.NET Identity для всіх.** Модель Identity (логін, пароль, lockout) — для персоналу. Гості
  без пароля з телефоном як ідентичністю в неї не вкладаються, а спільна схема дозволяє помилково
  авторизувати токен гостя на endpoint персоналу.
- **Окремий identity-провайдер** (Keycloak, OpenIddict як власний OAuth-сервер, Auth0, Entra ID).
  Keycloak — важкий контейнер на слабкому сервері; SaaS коштує грошей; власний OAuth-сервер —
  непропорційно складний для одного клієнта кожного типу. Може знадобитися для SSO персоналу мереж.
- **`initData` Telegram як токен на кожен запит.** Прив'язує API до Telegram, не дає додати інші
  канали й тягне персональні дані з Telegram у кожен запит. Власний JWT відділяє API від каналу.
- **Cookie для гостей.** TMA відкривається у webview Telegram з окремого піддомену й звертається до
  API на іншому; cookie потребують CORS із credentials і захисту від CSRF, а майбутній нативний
  застосунок усе одно працюватиме з bearer-токеном.

## Наслідки

**Що стає простішим**

- Компрометація або помилка на боці гостей не дає доступу до даних закладу через endpoints персоналу.
- Новий канал для гостей — новий верифікатор, без зміни токенів і API.
- Персонал отримує перевірену модель Identity (хешування паролів, lockout), а не власний код.

**Що стає складнішим**

- Два стеки автентифікації, і видача JWT гостям — власний код, чутливий до безпеки. Його треба
  тримати мінімальним і покритим тестами (підпис, `aud`, строк дії, свіжість `initData`).
- Без refresh-токенів сесія гостя залежить від доступності `initData`: поза Telegram (web-гість)
  знадобиться інший механізм.
- Відкликати токен гостя до закінчення строку не можна: блокування акаунта діє із запізненням до
  години.
- Для персоналу з кількома закладами членство перевіряється на кожен запит.

**Коли переглянути**

- З'являється нативний застосунок або web-гість без Telegram — потрібні refresh-токени.
- Мережі закладів хочуть SSO для персоналу — розглядаємо зовнішній identity-провайдер.
- Потрібне миттєве блокування гостей — список відкликаних токенів або коротший строк дії.

Пов'язані рішення: 0002 (контекст закладу), 0003 (OpenAPI), 0009 (ідентичність клієнта),
0012 (webhook).
