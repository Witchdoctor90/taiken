# 0009. Ідентичність клієнта: один акаунт на підтверджений телефон

## Статус

Proposed

## Контекст

Гість приходить у Taiken кількома шляхами:

- **Telegram Mini App** — канал MVP. Імовірно, до релізу не доживе, але й не заважає.
- **Нативний застосунок** — основний канал після MVP. Вхід через OTP, Google або Apple.
- **Анонімна оплата** — гість сканує QR і просто оплачує рахунок, без входу. Після оплати йому
  пропонують завантажити застосунок. Це очікуваний основний флоу для нових гостей.

Акаунт глобальний: одна людина — картки в кількох закладах (ADR 0002, ADR 0005). Бонуси
нараховуються лише за оплату через Taiken, тож оплата має знаходити свого власника, навіть якщо
людина увійшла вже після неї.

Вимоги:

- одна людина — рівно один акаунт, незалежно від того, яким способом вона входить;
- жодного ручного чи автоматичного злиття акаунтів;
- жодної анкети чи кроку реєстрації перед оплатою;
- мінімум власного security-коду (ADR 0005).

## Рішення

### Акаунт = підтверджений номер телефону

- `CustomerAccount` існує лише з підтвердженим номером. Номер — ключ акаунта (`phone_e164 UNIQUE`).
- Telegram і OTP — не окремі ідентичності, а **способи підтвердити номер**. Будь-який спосіб
  підтвердження закінчується одним викликом `ResolveOrCreate(VerifiedPhone)` у модулі Customers.
- Google, Apple та інші OIDC-провайдери номера не дають, тому акаунт не створюють. Вони — **швидкий
  вхід** в акаунт, номер якого вже підтверджено (див. нижче).
- Оскільки акаунт без номера не створюється, двох акаунтів однієї людини не виникає. Злиття
  акаунтів, коди прив'язки між каналами й таблиця «зовнішніх логінів» не потрібні.

```csharp
// Taiken.Customers.Contracts
public sealed record VerifiedPhone(PhoneE164 Phone, VerificationMethod Method, DateTimeOffset VerifiedAt);
public enum VerificationMethod { TelegramContact, Otp }
```

`ResolveOrCreate` — `INSERT … ON CONFLICT (phone_e164) DO NOTHING` + `SELECT`: два одночасні входи
з одним номером не створять дубль.

### Модель даних (схема `customers`)

```
customer_accounts   id, phone_e164 UNIQUE, display_name?, status, created_at
sign_in_bindings    method ('telegram'|'google'|'apple'|…), subject, customer_id, created_at
                    PK(method, subject)
consents            customer_id, type (processing|marketing), policy_version, granted_at, revoked_at?
```

- `sign_in_bindings` — не ідентичність, а запис «цей акаунт провайдера вже довів, що належить
  власнику номера». Акаунт тримається виключно на `phone_e164`; binding без акаунта не існує.
- `subject` — стабільний id у провайдера (`telegram_user_id`, OIDC `sub`), ніколи не email: email
  змінюється, а в Apple ще й прихований.
- Для OTP-входу binding немає: після OTP видаються токени (ADR 0005).
- `display_name` береться з першого джерела, що його дає (`first_name` у Telegram). Окремої анкети немає.
- `policy_version` у згоді фіксується в момент надання, не читається з поточної політики.

### Вхід через Telegram Mini App

```
TMA → POST /customers/auth/telegram { initData }
      ├─ HMAC initData + свіжість auth_date → telegram_user_id
      ├─ є binding (telegram, user_id) → customer_id → JWT
      └─ немає → 428 PhoneRequired
            TMA → WebApp.requestContact() → гість підтверджує
            Telegram → bot webhook (X-Telegram-Bot-Api-Secret-Token) → message.contact
                  ├─ contact.user_id == message.from.id, інакше ігнор
                  └─ ResolveOrCreate(VerifiedPhone(contact.phone, TelegramContact))
                     → sign_in_binding(telegram, from.id → customer_id)
            TMA повторює POST /customers/auth/telegram (коротке опитування) → JWT
```

- Номер вважається підтвердженим **лише** з бот-апдейту, де `contact.user_id == message.from.id`,
  тобто гість поділився своїм контактом, а не чужим. Відповідь `requestContact()` на клієнті лише
  сигналізує TMA, що можна повторити вхід; джерелом номера вона не є.
- Бот-webhook автентифікується секретом Telegram (`secret_token`), не схемами ADR 0005.

### Вхід через нативний застосунок (після MVP)

```
App → POST /customers/auth/otp/start  { phone }         → IOtpSender.Send
App → POST /customers/auth/otp/verify { phone, code }   → ResolveOrCreate(VerifiedPhone(phone, Otp)) → токени
```

- `IOtpSender` — порт у `Taiken.Channels.Abstractions`, у dev/staging — фейк, що пише код у лог.
- Обмеження частоти на номер і на IP, обмежена кількість спроб на код, строк дії коду — хвилини.
- Гість, який уже входив через Telegram, після OTP з тим самим номером потрапляє в той самий акаунт
  без жодних додаткових кроків.

### Вхід через Google, Apple та інші OIDC-провайдери (після MVP)

```
App → SDK провайдера → id_token
    → POST /customers/auth/oidc { provider, id_token, nonce }
      ├─ підпис через JWKS провайдера, iss, aud, exp, nonce → (provider, sub)
      ├─ є binding → токени
      └─ немає → 428 PhoneRequired + короткоживучий pending_binding_ticket
                 → OTP з тікетом → ResolveOrCreate → binding(provider, sub) → токени

Автентифікований гість → «Прив'язати Google/Apple» у налаштуваннях → binding без OTP
```

- Binding створюється лише у флоу, де номер щойно підтверджено, або з автентифікованої сесії.
- Валідація `id_token` на бекенді (`Microsoft.IdentityModel`, JWKS провайдера); застосунок
  використовує native SDK. Redirect-флоу OAuth і власний OAuth-сервер не потрібні (ADR 0005).
- Новий провайдер — нове значення `method` і валідатор токена, без змін у Customers.
- Google-вхід додається лише разом із Sign in with Apple (App Store Review Guideline 4.8).
- Застосунок з акаунтами має давати видалити акаунт зсередини; для Sign in with Apple при видаленні
  токени відкликаються через API Apple.

### Анонімна оплата і claim

- Оплата не вимагає входу. `payment_intents.customer_id = null`; intent отримує випадковий
  `claim_token` (≥128 біт, у БД зберігається лише хеш) і строк дії (30 днів).
- Екран результату показує CTA «завантаж застосунок». Токен передається через deep link, а як
  запасний шлях — короткий код на екрані (deep link часто губиться при інсталяції). Браузер тримає
  токени своїх оплат, тож кілька анонімних оплат забираються разом.
- Після входу застосунок викликає `POST /payments/claims { token }`. Claim дозволений лише для
  intent у статусі `succeeded` і лише раз. Результат — подія `PaymentClaimed(PaymentIntentId,
  CustomerId, VenueId)`.
- Loyalty обробляє `PaymentClaimed` так само, як `PaymentCompleted` з `CustomerId`. Ідемпотентність
  дає той самий унікальний індекс `stamp_entries(kind, source_type, source_id)` з `source_id` =
  intent. Штамп нараховується за правилами програми на момент claim.
- Короткий код підбирається перебором, тому на endpoint claim — обмеження частоти. Структура
  токена й таблиці — у ADR 0012.

### Інваріанти

- Номер нормалізується в E.164 до будь-якого збереження чи порівняння (Telegram віддає без `+`,
  користувач вводить як завгодно). Нормалізація — один тип `PhoneE164`, не рядок.
- Існуючий binding не перепризначається автоматично. Якщо `(method, subject)` уже прив'язаний до
  іншого акаунта або для прив'язаного Telegram прийшов контакт з іншим номером — 409, лог і ручний
  розбір.
- Номер акаунта в MVP не змінюється.

### Відхилені альтернативи

- **Ідентичність = канал** (`external_logins(provider, provider_key)` як ключ). Одна людина через
  TMA і через застосунок отримала б два акаунти, які довелося б зливати разом зі штампами. Злиття —
  складна, рідкісна й небезпечна операція, а номер телефону прибирає її потребу повністю.
- **Анкета при реєстрації.** Тертя в момент оплати; ім'я з Telegram достатнє, а анонімна оплата
  реєстрації не потребує взагалі.
- **Гостьовий акаунт для анонімної оплати** (акаунт без номера, прив'язаний до браузера). Порушує
  «акаунт = підтверджений номер» і повертає злиття. Claim окремої оплати простіший.
- **Email з Google/Apple як другий ключ акаунта.** Два ключі — два акаунти однієї людини і знову
  злиття. Email у Apple до того ж може бути relay-адресою.
- **Номер з відповіді `requestContact()` на клієнті.** Клієнт може підсунути довільний номер;
  підтвердженим вважається лише бот-апдейт від Telegram.

## Наслідки

**Що стає простішим**

- Один акаунт на людину без злиттів: новий спосіб входу — лише ще один спосіб отримати
  `VerifiedPhone`.
- Анонімна оплата не створює «напівакаунтів» у БД.
- Loyalty не знає про канали: і `PaymentCompleted`, і `PaymentClaimed` несуть лише `CustomerId`.

**Що стає складнішим**

- Перший вхід через TMA — у кілька кроків: запит контакту, бот-webhook, повторний вхід.
  Потрібен працюючий бот-webhook на staging.
- OTP — платні SMS і власний код обмеження частоти й спроб.
- Номер — персональні дані і ключ акаунта одночасно; його не можна просто «сховати» чи хешувати.
- Втрата доступу до номера = втрата доступу до акаунта, якщо до нього не прив'язано Google/Apple.
- Google/Apple вхід тягне обов'язки App Store: Sign in with Apple у парі й видалення акаунта.

**Коли переглянути**

- Рециклінг номерів оператором: новий власник номера через OTP потрапляє в чужий акаунт зі
  штампами. На 5–15 закладах — прийнятний ризик; з ростом — додатковий фактор або перевірка давності.
- Зміна номера власником — окремий флоу через OTP на новий номер (з сесії, у тому числі
  відкритої через Google/Apple).
- TMA прибирається — рядки `telegram` у `sign_in_bindings` і бот-webhook видаляються без змін у
  Customers.
- Гості без доступу до SMS (туристи без роумінгу) — OTP через месенджер як ще один спосіб
  підтвердити номер.

Пов'язані рішення: 0002 (ізоляція по закладу), 0005 (автентифікація), 0010 (QR-контракт),
0012 (PaymentIntent, claim).
