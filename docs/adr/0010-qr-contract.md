# 0010. QR-контракт: власний URL, код без внутрішніх id

## Статус

Proposed

## Контекст

Гість починає будь-який флоу зі сканування наліпки на столику. Наліпка — фізичний носій: її
друкують, клеять і не змінюють роками. Все, що в неї зашито, стає контрактом, змінити який можна
лише передруком у кожному закладі.

Канали клієнта різні й змінюватимуться (ADR 0009): анонімна web-оплата — основний флоу, нативний
застосунок — після MVP, Telegram Mini App — тестовий канал, який імовірно не доживе до релізу.
Наліпка не має залежати від жодного з них.

Анонімний запит не має автентифікації, тож контекст закладу для нього може дати лише сам QR
(ADR 0002).

## Рішення

### QR кодує власний URL

```
https://<domain>/q/{code}
```

Канал обирається після сканування, а не при друку:

```
https://<domain>/q/AB12CD7K
   ├─ застосунок встановлено → Universal Link (iOS) / App Link (Android) → застосунок з кодом
   ├─ інакше                 → web: рахунок → анонімна оплата → CTA «завантаж застосунок»
   └─ staging               → кнопка «Відкрити в Telegram» → t.me/<bot>/app?startapp=q_AB12CD7K
```

- Контракт наліпки — лише шлях `/q/{code}`. Жодних query-параметрів зі змістом, жодних id закладу
  чи столика.
- `startapp=q_{code}` — внутрішній формат TMA, не контракт наліпки. TMA отримує код зі
  `start_param` і далі працює так само, як web.
- Той самий URL без змін записується в NFC-мітку.
- Для Universal/App Links домен віддає `/.well-known/apple-app-site-association` і
  `/.well-known/assetlinks.json` (з появою застосунку).

### Код

```
table_qr_codes   code PK, venue_id, table_ref, status ('active'|'disabled'), created_at, updated_at
```

- 8 символів Crockford base32 (без `0/O`, `1/I/L`), генерується випадково (~40 біт). Не
  послідовний і не виводиться з id.
- Код ніколи не перевикористовується. Вимкнений код лишається мертвим назавжди, щоб стара
  наліпка не почала вести в чужий заклад.
- Код можна перепризначити на інший столик у межах того ж закладу. Переносу між закладами немає —
  новий код.
- Невідомий або вимкнений код — одна й та сама відповідь «наліпка недійсна», без розрізнення.

### Контекст закладу

- `code → (venue_id, table_ref)` резолвить модуль Venues. Це єдине джерело контексту закладу для
  анонімних запитів гостя; клієнт ніколи не передає `venue_id` сам (ADR 0002).
- `GET /tables/{code}/bill` і `POST /payments/intents { code, billVersion }` приймають код, не id.
- На endpoints з кодом — обмеження частоти за IP, щоб перебір кодів не був практичним.

### Домен

- На MVP — тимчасовий домен; у документах і коді — плейсхолдер `<domain>`, значення з конфігурації.
- Наліпки MVP — лише демо, їх передрук нічого не коштує.
- Постійний домен обирається до першого друку для справжнього закладу. Після переходу тимчасовий
  домен тримає 301 на новий на `/q/{code}`, доки не лишиться жодної старої наліпки.

### Відхилені альтернативи

- **`t.me/<bot>/app?startapp=q_{code}` у QR.** Прив'язує фізичну наліпку до тестового каналу:
  відмова від TMA — передрук у всіх закладах.
- **Id закладу й столика в URL** (`/v/{venueId}/t/{table}`). Світить внутрішні id, дає перебір
  столиків, не дозволяє перепризначити наліпку.
- **Підписаний токен у QR.** Нічого не додає: код і так публічний, бо висить на столі, а
  відкликання простіше через `status`, ніж через ротацію ключів.

## Наслідки

**Що стає простішим**

- Канали клієнта можна додавати й прибирати без передруку наліпок.
- Наліпку можна перепризначити або вимкнути з адмінки.
- NFC — той самий контракт, без окремої моделі.

**Що стає складнішим**

- Потрібна власна web-сторінка `/q/{code}` навіть тоді, коли основний канал — застосунок.
- Домен стає незворотним рішенням з моменту друку для справжніх закладів.
- Universal/App Links прив'язані до домену: зміна домену — оновлення конфігурації застосунку.

**Відомий ризик**

- Код не секрет. Хто сфотографував наліпку, може віддалено бачити відкритий рахунок цього
  столика й оплатити його. У рахунку немає персональних даних, а оплата чужого рахунку шкоди не
  завдає, тож для MVP це прийнятно.

**Коли переглянути**

- Перший друк для справжнього закладу — постійний домен.
- QR не для столика (каса, take-away) — `table_ref` nullable або поле `kind`.
- Скарги на віддалений перегляд рахунків — показувати рахунок лише з підтвердженням присутності
  (NFC, код від офіціанта).

Пов'язані рішення: 0002 (ізоляція по закладу), 0009 (канали й анонімна оплата),
0012 (PaymentIntent).
