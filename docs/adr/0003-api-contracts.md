# 0003. Контракти API: C# → OpenAPI → TS-клієнт

## Статус

Proposed

## Контекст

Бекенд на .NET, клієнти — на TypeScript: у MVP це Telegram Mini App (`web/apps/customer-tma`), далі
з'являться адмінка персоналу й, можливо, нативний застосунок. Бекенд і фронтенд пише одна людина
разом з агентом, в одному репо.

Що треба забезпечити:

- **Без дрейфу типів.** Зміна DTO на бекенді має ламати компіляцію фронтенду, а не сторінку в
  Telegram у гостя.
- **Одне джерело правди.** Друге джерело, яке оновлюють вручну, відстає першим.
- **Видимі зміни API.** Ламаючу зміну має бути видно на рев'ю PR, а не після деплою.
- **Мінімум нової інфраструктури.** Нічого, що треба підтримувати окремо від коду.

## Рішення

### Джерело правди — код C# (code-first)

- Контракт HTTP API — це endpoints і їхні request/response DTO у C#. OpenAPI-документ генерується
  з коду, TS-клієнт генерується з OpenAPI. Руками не пишеться ні специфікація, ні TS-типи.
- Документ генерує вбудований `Microsoft.AspNetCore.OpenApi` під час білду (build-time generation).
- Endpoints повертають `TypedResults` / `Results<…>`, щоб типи відповідей і коди статусів потрапляли
  в документ із сигнатури, а не з ручних атрибутів.

### HTTP DTO — не те саме, що `Contracts` модуля і не доменні сутності

- `Taiken.<Name>.Contracts` (ADR 0001) — для взаємодії модулів усередині процесу. Назовні по HTTP
  вони не віддаються.
- HTTP DTO живуть поруч з endpoints у реалізації модуля. Так внутрішній контракт між модулями і
  зовнішній контракт з клієнтами змінюються незалежно, а доменні сутності ніколи не серіалізуються
  напряму.

### Документ на аудиторію

- Окремий OpenAPI-документ на кожен тип клієнта. У MVP — один: `customer` (API для TMA). Документ
  `staff` з'явиться разом з адмінкою.
- Webhooks провайдерів, dev-endpoints і health checks у клієнтські документи не потрапляють.

### Спільні конвенції схеми

- **Strongly-typed ID** (`VenueId`, `PaymentIntentId`, …) серіалізуються як рядок і описуються в
  схемі як `string` (`format: uuid`) — через JSON-конвертер і schema transformer. Інакше в
  TS-клієнті вони стали б об'єктами.
- **Гроші** — `{ amountMinor: integer, currency: string }` (ISO 4217). Мінорні одиниці, як у
  `Money` (ADR 0001, Shared). Суми в межах закладу далекі від меж точності `number` у JS.
- **Enum** — рядками (`JsonStringEnumConverter`), у TS стають union-типами.
- **Nullable** — з nullable reference types C#: що не nullable в C#, те required у схемі.
- **Помилки** — RFC 7807 `ProblemDetails` зі стабільним машинним полем `code`
  (`bill_version_changed`, `phone_pending`, …). Клієнт розгалужується за `code`, а не за текстом.

### Генерація й перевірка в CI

1. `dotnet build` генерує `src/Host/Taiken.Api/openapi/customer.json`. Файл закомічений.
2. .NET-job у CI після білду перевіряє `git diff --exit-code` на цьому файлі. Змінив API і не
   закомітив документ — CI червоний. Змінений документ — це і є видимий на рев'ю diff API.
3. `@taiken/api-client` у `web/packages/` генерується з цього файлу: типи — `openapi-typescript`,
   HTTP-клієнт — `openapi-fetch`. Згенерований код закомічений.
4. Web-job запускається і на зміни `src/Host/Taiken.Api/openapi/**`, регенерує клієнт і перевіряє
   diff. Зміна API без оновленого клієнта — CI червоний.

### Версіонування — поки ні

Поки єдиний клієнт живе в тому самому репо й деплоїться разом із бекендом, ламаючі зміни
дозволені: їх ловить компілятор TS у тому самому PR. Версіонування API з'являється разом із першим
клієнтом, якого не можна оновити синхронно (нативний застосунок, зовнішній інтегратор).

### Відхилені альтернативи

- **Spec-first** (OpenAPI YAML пишеться руками, з нього генеруються серверні заглушки). Ще один
  артефакт, який треба підтримувати вручну; генератори серверного коду для ASP.NET слабкі, а
  перевага — контракт до коду — важлива для кількох команд, а не для однієї людини.
- **TS-типи руками.** Дрейфують із першого ж перейменування поля.
- **Swashbuckle / NSwag для документа.** Swashbuckle більше не входить у шаблони ASP.NET, вбудований
  генератор підтримує Microsoft. NSwag уміє генерувати й TS-клієнт, але тягне власний runtime і
  конфігурацію.
- **Orval** (генерація react-query хуків). Зручно, але генерує runtime-логіку і прив'язує клієнт до
  конкретної бібліотеки запитів. `openapi-typescript` + `openapi-fetch` — лише типи й тонкий
  типізований `fetch`; обгортку в TanStack Query можна додати руками, коли знадобиться.
- **Kiota.** Важкий runtime і стиль клієнта, орієнтований на великі API.
- **tRPC / GraphQL.** tRPC не працює з .NET-бекендом; GraphQL — окрема модель і інфраструктура,
  непропорційна одному клієнту з десятком endpoints.

## Наслідки

**Що стає простішим**

- Типи фронтенду завжди відповідають бекенду: розбіжність — це помилка компіляції або червоний CI.
- Зміни API видно на рев'ю як diff `customer.json`, включно з ламаючими.
- Агент, який змінює endpoint, отримує негайний зворотний зв'язок від CI, а не від гостя в Telegram.

**Що стає складнішим**

- Якість контракту залежить від дисципліни в endpoints: `TypedResults`, коректні nullable, явні коди
  помилок. Endpoint, що повертає `IResult` без типу, дає в документі порожню відповідь.
- Schema transformers для strongly-typed ID і `Money` — власний код, який треба підтримувати при
  появі нових типів.
- CI зв'язаний: зміна бекенду запускає web-job через шлях до документа, а web-job залежить від
  згенерованого бекендом файлу.
- Відсутність версіонування — свідомий борг. Перший клієнт поза репо вимагатиме рішення.

**Коли переглянути**

- З'являється клієнт, якого не можна оновити одночасно з бекендом, — вводимо версіонування.
- API починають споживати треті сторони — потрібні стабільність, changelog і, можливо, spec-first.
