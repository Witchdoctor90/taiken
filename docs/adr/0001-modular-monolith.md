# 0001. Модульний моноліт, правила залежностей, без FK між схемами модулів

## Статус

Proposed

## Контекст

Taiken Core — бекенд оплати й лояльності для закладів Албанії. Обмеження, які визначають форму
системи:

- **Команда.** Один розробник, значну частину коду пише агент (Claude Code). Межі в коді мають
  перевірятися машиною, а не триматися на пам'яті й дисципліні.
- **Навантаження.** 5–15 закладів на старті, ~60–70 оплат на день на заклад. Тривіально для одного
  процесу й однієї бази.
- **Інфраструктура й бюджет.** Нульовий бюджет, один власний сервер (Windows 10 + Docker) за
  Cloudflare Tunnel. Кожен додатковий процес чи база — це операційна робота на одну людину.
- **Строки.** MVP-демо орієнтовно до кінця жовтня 2026.
- **Домен.** Уже зараз видно окремі bounded contexts з різними правилами: Customers (глобальний,
  поза закладами), Venues, Payments, Loyalty. Після MVP додадуться Menu, Ordering, аналітика.
- **Консистентність.** Оплата — якір системи: зміна стану платежу і подія `PaymentCompleted`, яку
  споживає Loyalty, мають бути атомарними відносно одна одної. У розподіленій системі це вимагало б
  саг чи двофазних комітів.

Потрібна форма, яка сьогодні дешева як один процес, але зберігає межі між контекстами настільки
чисто, щоб модуль згодом можна було винести окремо без переписування.

## Рішення

### Один процес, модулі як bounded contexts

- Система — один deployable: `src/Host/Taiken.Api`. Host — єдиний composition root.
- Кожен bounded context — модуль із двох проєктів:
  - `Taiken.<Name>.Contracts` — публічні інтеграційні події, DTO, інтерфейси запитів до модуля;
  - `Taiken.<Name>` — домен, EF, handlers, endpoints. Усе `internal`, крім Wolverine handlers
    (`public`, бо Wolverine за замовчуванням знаходить лише public-типи).
- Шари всередині модуля — папки, не окремі проєкти.
- Модуль підключається до хоста через `AddXModule(IServiceCollection, IConfiguration)` і
  `MapXEndpoints(IEndpointRouteBuilder)`. Host лише викликає їх.

### Взаємодія між модулями

- **Синхронно** — лише через інтерфейси з `Contracts` іншого модуля, в межах процесу.
- **Асинхронно** — інтеграційними подіями з `Contracts` через Wolverine + transactional outbox
  (деталі — ADR 0004).
- Модуль ніколи не посилається на реалізацію іншого модуля і не читає його таблиці.

### Дані

- Одна база Postgres; **кожен модуль — власна схема**, власний `DbContext`, власні міграції.
- **Жодних foreign key між схемами модулів.** Ідентифікатор з іншого модуля (`customer_id` у
  `loyalty`) — просто значення. Його існування перевіряється через `Contracts` у момент запису, а
  подальша узгодженість — подіями.
- FK усередині схеми модуля — звичайна практика, обмеження не стосується.

### Правила залежностей між проєктами

| Проєкт | Може посилатися на |
|---|---|
| `Taiken.<Name>.Contracts` | `Shared` |
| `Taiken.<Name>` | свої `Contracts`, чужі `*.Contracts`, `Shared`, `Integrations/*/*.Abstractions` |
| `Integrations/<Kind>/Taiken.<Kind>.Abstractions` | `Shared` |
| `Integrations/<Kind>/Taiken.<Kind>.<Provider>` | свої `Abstractions`, `Shared` |
| `Core/*` | інші `Core`; ніколи — `Modules`, `Integrations`, `Fakes` |
| `Fakes/*` | нічого з `src/` |
| `Host/Taiken.Api` | усе, крім `Fakes` |

Правила закріплюються `Taiken.ArchitectureTests` (з M2, TAI-12), які запускаються в CI. До того
вони живуть у README папок і `CLAUDE.md`.

### Відхилені альтернативи

- **Шаровий моноліт без модулів** (один проєкт або шари Domain/Application/Infrastructure на всю
  систему). Найшвидший старт, але межі між контекстами тримаються лише на домовленостях і
  розмиваються з першого «швидкого» join'а. Із кодом, який генерує агент, це відбудеться раніше, ніж
  з'явиться потреба щось винести.
- **Мікросервіси з першого дня.** Зв'язка «оплата → штамп» стає розподіленою транзакцією; кожен
  сервіс — окремий контейнер, база, деплой і моніторинг на одному домашньому сервері й одній людині.
  При поточному навантаженні незалежне масштабування не дає нічого.
- **Три проєкти на модуль** (Contracts · Core · Infrastructure), як у першій версії плану. Межа, яка
  має значення, проходить між модулями, а не між шарами всередині модуля; `internal` і
  ArchitectureTests тримають її краще, ніж зайві проєкти. Три проєкти на модуль — це ~12 проєктів
  на MVP без відчутної користі.
- **FK між схемами.** Дають цілісність на рівні бази, але зв'язують модулі через БД: порядок
  міграцій стає спільним, а винесення модуля в окрему базу вимагає спершу розрізати ключі.
- **Окрема база на модуль.** Та сама логічна межа, що й схема, але вдвічі-вчетверо більше
  інстансів, бекапів і рядків підключення. Схема + заборона крос-схемних FK зберігають можливість
  перейти на окремі бази пізніше.

## Наслідки

**Що стає простішим**

- Один процес, один деплой, одна база, один бекап — операційно посильно для однієї людини.
- Виклики між модулями — в межах процесу; зміна стану й публікація події — в одній локальній
  транзакції через outbox, без розподілених транзакцій.
- Межі перевіряються машиною. Агент, який порушить правило залежностей, отримає червоний CI, а не
  тихий технічний борг.
- Шлях до винесення модуля готовий: `Contracts` стають API або повідомленнями, схема — окремою
  базою, і крос-схемних FK, які треба розрізати, немає.

**Що стає складнішим**

- Цілісність між модулями тримається кодом і тестами, а не базою. Можливий, наприклад, запис у
  `loyalty` з `customer_id`, якого вже немає. Компенсація: перевірка через `Contracts` при записі,
  події про видалення/деактивацію, м'яке видалення глобальних сутностей.
- SQL-join'и між модулями неможливі. Звіти й статистика поверх кількох модулів потребуватимуть
  read-моделей або проекцій (окремий модуль Analytics — коли запити стануть важкими).
- Між модулями — eventual consistency: картка лояльності оновлюється після `PaymentCompleted`, а не
  в тій самій транзакції, що й оплата. UI має це враховувати.
- Один процес і одна база — спільна точка відмови. Падіння чи перевантаження одного модуля зачіпає
  всі. На поточному масштабі прийнятно.
- Wolverine handlers — виняток із правила `internal`; межу для них тримають лише ArchitectureTests.

**Коли переглянути**

- Модулю потрібне незалежне масштабування або окремий цикл релізів.
- Над кодом працює більше однієї-двох людей, і спільний деплой почне заважати.
- Профіль навантаження одного модуля (наприклад, аналітики) почне шкодити решті.
