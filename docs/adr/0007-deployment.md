# 0007. Deployment: власний сервер, Cloudflare Tunnel, staging, бекапи

## Статус

Proposed

## Контекст

- **Бюджет — нульовий.** Хмарний хостинг, керована база й платні сервіси моніторингу виключені.
- **Залізо є.** Власний сервер: Windows 10 + Docker, домашнє підключення без статичної IP-адреси.
- **Операції — одна людина.** Усе, що вимагає ручних дій при кожному деплої або постійного
  нагляду, рано чи пізно не буде зроблено.
- **Репо публічне.** Усе, що має доступ до сервера з CI, фактично доступне будь-кому, хто відкриє PR.
- **Дані.** Taiken не бачить даних карток (SAQ A), але зберігає персональні дані гостей (телефон,
  ім'я), стан оплат і зашифровані облікові дані PSP закладів. Їх втрата або витік — реальна шкода.
- **Цілі.** Staging для демо MVP (повний флоу в Telegram) зараз; prod — з першим пілотним закладом.

## Рішення

### Середовище виконання

- Усе працює в Docker Compose на власному сервері. Сервіси: `api`, `web`, `postgres`, `cloudflared`,
  `backup`; у staging додатково `fakepos` і `fakepsp`. У prod фейків немає ніколи.
- Кожне середовище — окремий compose-проєкт (`taiken-staging`, пізніше `taiken-prod`) зі своїми
  базою, volumes, `.env`, Telegram-ботом і hostnames. Спільного між середовищами немає нічого,
  крім заліза.
- Базовий `deploy/compose.yaml` + override на середовище (TAI-11), а не окремі
  незалежні файли.
- `restart: unless-stopped` для всіх сервісів; ротація логів контейнерів (`max-size`, `max-file`),
  щоб логи не заповнили диск.

### Мережа — Cloudflare Tunnel, жодних відкритих портів

- Назовні через Tunnel публікуються лише: `app.` (TMA), `api.`, у staging — `fakepsp.` (HPP в
  iframe). TLS термінує Cloudflare.
- Усе інше — у внутрішній мережі Docker: `api` ↔ `postgres`, `api` → `fakepos`, webhook `fakepsp` →
  `api`. Postgres назовні не видно.
- Адмінки фейків і будь-які службові сторінки — за Cloudflare Access. TMA і API за Access бути не
  можуть: до них звертаються Telegram і гості.

### Доставка — pull, а не push

- GitHub Actions збирає образи й публікує в GHCR. На сервері агент (Watchtower або аналог) сам
  підтягує нові образи.
- Staging іде за тегом `main` автоматично. Prod — лише за явним тегом версії, який оновлюється
  вручну. `latest` у prod не використовується.
- Ні self-hosted runner'а, ні SSH-доступу з CI: у GitHub немає жодного секрету, який дає доступ до
  сервера. Для публічного репо це принципово.
- Згенерований код Wolverine збирається в образ (ADR 0004).

### Міграції

- `api` застосовує EF-міграції своїх модулів на старті. Це безпечно, поки екземпляр `api` один.
- Автоматично застосовуються лише адитивні міграції. Міграція, що видаляє чи перейменовує
  колонки або таблиці з даними, потребує ручного кроку й свіжого бекапу.

### Секрети

- `.env` на сервері, поза репо, з доступом лише для облікового запису, під яким працює Docker.
  У ньому: токен бота, ключ підпису JWT (ADR 0005), HMAC-секрет Fake PSP.
- Ключі ASP.NET Data Protection — у volume поза контейнером (ADR 0005).

### Бекапи

- Контейнер `backup` за розкладом робить `pg_dump`, шифрує дамп і вивантажує в Cloudflare R2.
  Дампи містять персональні дані, тому незашифрованими вони сервер не залишають.
- Разом із базою бекапляться ключі Data Protection і `.env` (теж зашифровано). Дамп без ключів
  означає нечитабельні облікові дані PSP.
- Зберігання: щоденні за останній тиждень, щотижневі за останній місяць.
- Бекап вважається робочим лише після перевіреного відновлення. Відновлення в окремий
  compose-проєкт перевіряється регулярно, а не в день аварії.

### Моніторинг — мінімальний

- Зовнішня безкоштовна перевірка доступності `/health/ready` через Tunnel зі сповіщенням у Telegram.
- Помилки рівня Error, включно з dead letters (ADR 0004), мають доходити до людини, а не лише
  лежати в логах контейнера.

### Сервер

- Вимкнений сон, автозапуск Docker після перезавантаження, керовані вікна оновлень ОС.
- Windows 10 вийшла з основної підтримки в жовтні 2025 року, а розширені оновлення безпеки для
  домашніх користувачів завершуються в жовтні 2026-го. Крім того, Docker на Windows стартує разом
  із сесією користувача. Тому **перенесення хоста на Linux на тому самому залізі — передумова prod**,
  але не staging-демо.

### Відхилені альтернативи

- **VPS або PaaS.** Надійніше за домашній сервер, але коштує грошей щомісяця. Перший кандидат, коли
  з'явиться бюджет або вимоги до доступності від закладів.
- **Проброс портів + reverse proxy (Caddy/nginx).** Потребує статичної адреси або DDNS, відкриває
  домашню IP-адресу й порти в інтернет, TLS і захист від DDoS — власна турбота.
- **Self-hosted GitHub runner або SSH-деплой з CI.** Push-модель тримає доступ до сервера в CI; для
  публічного репо це ризик виконання чужого коду на сервері.
- **Kubernetes / k3s.** Непропорційно для одного вузла й одного екземпляра кожного сервісу.
- **Керована Postgres.** Коштує грошей і додає мережеву затримку до кожного запиту.

## Наслідки

**Що стає простішим**

- Нульова вартість, жодних відкритих портів, TLS і захист периметра — на боці Cloudflare.
- Деплой staging — це merge у `main`. Жодних ручних кроків і жодних секретів сервера в GitHub.
- Середовища ізольовані одне від одного на рівні compose-проєктів.

**Що стає складнішим**

- Одна машина — одна точка відмови. Вимкнене світло чи інтернет означає, що оплата через Taiken
  недоступна; гість платить закладу звичайним способом, але штамп не отримає.
- Staging і prod ділять ресурси: навантаження на staging може впливати на prod.
- Концентрація на Cloudflare: Tunnel, Access і R2 — один постачальник.
- Pull-деплой не видно в GitHub: статус і час деплою треба дивитись на сервері. Відкат — перетег образу.
- Міграції на старті `api` не підходять для кількох екземплярів.
- Безпека хоста на Windows 10 без оновлень — неприйнятна для prod.

**Коли переглянути**

- **До першого пілотного закладу:** хост на Linux; оцінити VPS для prod.
- Потрібен більш ніж один екземпляр `api` — міграції виносяться в окремий крок.
- Заклади вимагають гарантій доступності — VPS або хмара замість домашнього сервера.
