# 0006. Публікація пакетів: ProjectReference до першого зовнішнього споживача

## Статус

Proposed

## Контекст

У репо живуть .NET-проєкти, які посилаються один на одного (`Shared`, `*.Contracts`,
`*.Abstractions`), і web-пакети в pnpm workspace (`@taiken/api-client`, `@taiken/config`). Екосистема
Taiken з часом може вийти за межі цього репо: окремі сервіси, застосунки, інтеграції партнерів.

Звідси спокуса одразу оформити спільний код як пакети з версіями й фідом «на майбутнє». Але зараз:

- усі споживачі цих проєктів — в одному репо й в одному білді;
- код пише одна людина, і більшість змін зачіпає кілька проєктів одночасно;
- контракти ще активно змінюються.

Опубліковані пакети для такої ситуації означають, що кожна наскрізна зміна перетворюється на
«опублікувати → підняти версію → оновити споживача», а між версіями виникає розсинхрон.

## Рішення

### Всередині репо — лише посилання на вихідний код

- .NET — тільки `ProjectReference`. Web — тільки `workspace:*` у pnpm.
- Внутрішнього NuGet- чи npm-фіду немає, версій у внутрішніх пакетів немає.
- `IsPackable=false` за замовчуванням для всіх .NET-проєктів (`Directory.Build.props`). Пакування
  вмикається явно й поштучно.

### Коли пакет з'являється

- Тригер — **перший зовнішній споживач**: код поза білдом цього репо, який має компілюватися проти
  наших типів (окремий репо, сервіс, SDK для партнера).
- Не тригер: інший модуль у тому самому хості, TMA чи адмінка в `web/`, тести.
- Публікується лише те, що потрібно зовнішньому споживачу, і лише з цих категорій:
  `*.Contracts`, `Integrations/*/*.Abstractions`, `Shared`, `@taiken/api-client`.
  Реалізації модулів і адаптерів не публікуються ніколи.
- Фід — GitHub Packages (NuGet і npm) того ж репо. Версіонування — SemVer. Інструмент для
  версій (з git-тегів тощо) обирається тоді, коли з'явиться перший пакет.
- Після публікації пакет еволюціонує за тими самими правилами, що й інтеграційні події (ADR 0004):
  адитивно; ламаюча зміна — нова major-версія.

### Відхилені альтернативи

- **Пакети й фід з першого дня.** Кожна наскрізна зміна — три кроки замість одного коміту;
  розсинхрон версій між проєктами одного репо; час на CI публікації, який нікому не потрібен.
- **Окремі репо на модуль.** Суперечить модульному моноліту (ADR 0001) і робить атомарні зміни
  неможливими.
- **Git submodules.** Та сама проблема розсинхрону, плюс незручна робота з гілками.
- **Копіювання спільного коду в зовнішні репо.** Дрейфує з першого ж виправлення.

## Наслідки

**Що стає простішим**

- Зміна контракту разом з усіма споживачами — один коміт і один PR; компілятор знаходить усі місця.
- Жодного розсинхрону версій і жодної інфраструктури публікації, яку треба підтримувати.
- Шлях до пакетів уже закладений: `IsPackable` вмикається поштучно, категорії кандидатів визначені.

**Що стає складнішим**

- Поки нічого не опубліковано, ніщо не змушує тримати `Contracts` стабільними. Межі тримають
  ArchitectureTests (ADR 0001), але не стабільність API.
- Перший зовнішній споживач вимагатиме роботи одразу: CI публікації, версіонування, changelog і
  стабілізація вже наявних контрактів заднім числом.
- Опублікований `Shared` нав'язує свою стабільність усім модулям, які від нього залежать.
  Тому публікувати його варто лише тоді, коли без нього зовнішній споживач справді не обійдеться.

**Коли переглянути**

- З'являється перший зовнішній споживач.
- Кількість людей, які працюють над кодом, зростає настільки, що атомарні зміни через увесь репо
  стають проблемою, а не перевагою.

Пов'язані рішення: 0001 (модульний моноліт), 0003 (`@taiken/api-client`), 0004 (еволюція контрактів).
